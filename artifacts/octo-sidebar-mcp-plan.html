02 / Revised direction · CLI-owned MCP

Octo remains a harness of harnesses.

Configure and authenticate MCP in the CLI you already use. That CLI discovers and executes its tools. Octo provides the conversation, displays activity, and relays requests that need your input.

Yes, this is possible—and it is the right boundary for Octo. The previous proposal went further into server management than needed. Native server setup, config editing, credential storage and independent MCP connections are out of scope for this direction.

What “authorized” means

Octo usually needs no separate MCP identity: the CLI process it launches uses that CLI’s configured credentials and policies. The agent inside the CLI performs the tool call. This does not create an app-wide pool of tools that all providers can share.

Codex supports shared host MCP configuration and trusted project overrides. When the executable, configuration home, environment and project context match, inheriting those tools is the intended integration path. Availability still depends on account access and policy. Official MCP guide ↗

Example: configure a documentation MCP server in Codex, authenticate there if required, then use a Codex chat in Octo. Codex decides whether to call that server and returns the result through its existing event stream. Switching to another provider uses that provider’s own configuration.

The implemented native bridge

Show: server/tool names, progress, completion and errors from harness events.

Ask: render approval or structured-input requests and return the explicit response through the provider adapter.

Explain: if a connection needs login, identify the CLI that owns setup and authentication. A read-only list of harness-reported tools could be useful later.

Connecting a server and approving an action are separate. Existing approval and sandbox boundaries remain authoritative. The integration must never grant blanket approval to make tools work.

Where Octo is today

JSONLineProcess launches the selected CLI with the checkout and inherited process environment. Codex already uses app-server. Its configured tools may therefore be available to the model today, but this report has not exercised a live MCP call.

CodexHarness now maps MCP lifecycle events into stable, bounded tool activity and validates native forms, app-access choices and tool questions. Decisions remain outside collapsed work; provider resolution and shutdown invalidate stale cards. Unsupported schemas receive a visible notice and a non-consenting response.

Claude’s current adapter launches print mode, shows generic tool-use activity, and reports denied operations. It has no interactive approval bridge and has not been runtime-validated on this Mac. Other harnesses need their own capability checks; Codex authentication does not automatically transfer to them.

Computer Use approvals: verified boundary

The native card shows the target app, provider message and only validated schema choices. It returns exact form values: once, session, or always where advertised, with matching persistence metadata only for explicit scope choices. Metadata alone never adds permission. Generic Allow is never made permanent. Unsupported nested/array/format/secret/device/URL requests are declined explicitly.

T3 PR #8058 provided the app-access fixture reference. Issue #8318 describes a separate Windows transport failure before approval. No workaround was applied to macOS. Codex and its configured service alone own screenshots, accessibility, clicks and typing.

Another CLI integrates by declaring each HarnessCapabilities field, emitting ToolActivity/AgentInteraction, and implementing typed response mapping plus lifecycle invalidation in its adapter. Shared SwiftUI views remain unchanged. Claude reports its unavailable interaction capabilities.

Limits to inheritance

A GUI-launched CLI may receive different environment variables from an interactive shell. The chosen executable, configuration home, project trust and account must be checked before promising parity. Desktop-only host tools and hosted plugins may depend on services the standalone CLI does not expose. A CLI restart/reconnect must respect active work and per-thread process ownership.
