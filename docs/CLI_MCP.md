# CLI-owned integrations

Octo is the native interaction layer. Each CLI owns configuration, discovery, connections, authentication, credentials, execution, and permission policy. Octo does not implement an MCP client, server setup UI, credential store, shared tool pool, or computer-control engine. Inventory is not required to run tools and is not implemented.

## Implemented support

| Capability | Codex adapter | Claude SDK stream adapter |
| --- | --- | --- |
| MCP call name, progress, completion, failure | Yes, stable identity and bounded details | Stable tool-use/result identity; no argument dump |
| Text / structured result summaries | Yes; limits and redaction below | Bounded/redacted text; structured summaries unavailable |
| Primitive forms | Strings, booleans, finite numbers/integers, single string choices | Unavailable |
| Computer Use app-access decisions | Validated forms; exact choices and explicit submission | Unavailable |
| Tool questions | CLI 0.158+ experimental opt-in; choices and text | Single-choice AskUserQuestion with free text; multi-select declined |
| Inventory, URL auth, device verification | Unavailable | Unavailable |
| Images/audio/resources or embedded MCP apps | Omitted from result details | Unavailable |

Schema support, Octo UI support, and actual tool availability are different. The generated schema supports more forms than this UI. Arrays, nested objects, formats, patterns, unknown constraints, oversized fields, secret questions, URL elicitation, and device verification are rejected explicitly. No unsupported field is silently dropped to approve a request. Unsupported MCP requests receive decline with null content and a visible notice. Unsupported questions receive an empty answer map and a notice.

Forms have at most 16 fields and 32 choices per field. Responses validate field identity, types, required values, advertised choices, finite/integral numbers and supported bounds. No provider default is selected or submitted automatically. Requests and form answers are session-only; Octo does not archive them. The provider may independently retain answers in its own history.

Computer Use requests show the provider's message and app identity from its metadata (or the narrowly recognized `Allow ChatGPT to use …?` message). Enum/oneOf values are returned unchanged. The adapter recognizes exact `session` and `always` choices on `approval`/`persist` fields and explicit boolean `session`/`always` fields, adding the corresponding `_meta.persist` only for that explicit selection. Ordinary form metadata alone never creates a choice; the recognized Computer Use extension below is handled separately. Generic `allow` never becomes persistent consent. Other scope conventions remain ordinary exact form values; Octo does not infer persistence from substrings. Conflicting durations cannot be submitted. Cancel and Decline remain distinct MCP actions. Tool questions have no protocol decline/cancel action: Cancel sends `answers: {}` and the UI explains this; Stop interrupts the turn.

### Computer Use approval duration

For the installed Computer Use extension's empty `form` requests, Octo now recognizes `_meta.codex_approval_kind: "mcp_tool_call"`, `connector_id: "computer-use"`, a nonempty `tool_name`, `tool_params.app`, and a bounded, unique `persist` array containing `session` and/or `always`. These provider-advertised scopes appear as **Allow for this chat session** and **Always allow this app**, alongside **Allow once**, Decline and Cancel. App display names retain the bundle identifier. Short choice lists use visible native radio buttons; consent starts unset and requires Submit response.

The duration field exists only in Octo's UI. Responses preserve empty form `content: {}` and send `_meta.persist` only for an explicitly selected advertised duration. Once omits persistence metadata; decline/cancel retain null content. Nonempty forms keep their schema-defined choices, and unrelated or malformed metadata cannot add durations. Octo does not cache consent, auto-answer subsequent requests, or broaden permissions across apps/chats; retention and enforcement belong to the integration. The session option is not a promise that a provider grant survives disconnect/relaunch. Audio-only requests without an app identity are outside this extension mapping.

Evidence: bundled Codex CLI **0.158.0-alpha.2.1** app-server v2 generated `McpServerElicitationRequestParams/Response`, and installed Computer Use **1.0.1001242** `@oai/cua` macOS `computer-use-policy.js`, inspected 2026-09-27. That policy sends `persist: ["session", "always"]` when persistent approval is allowed, otherwise `["session"]`, in metadata instead of form properties. This is a versioned integration convention beyond the generic [official elicitation contract](https://learn.chatgpt.com/docs/app-server#mcp-server-elicitation-requests).

Verification: **77 Swift tests pass**, including exact metadata responses, empty content, missing/invalid/unadvertised scope rejection, schema non-broadening, stale responses, and fragmented fixture delivery. Native build and signature checks pass. Isolated native smoke verified visible choices, disabled submission before selection, session/always responses, cancellation with null content, and fresh unset state on a new request. The test fixture deliberately continues requesting decisions; no real app authorization or paid model call was made. Real Computer Use retention across calls/turns remains unverified.

## Ownership and lifecycle

`HarnessCapabilities`, `AgentInteraction`, `InteractionField`, and `AgentInteractionResponse` extend the existing contract. `ToolActivity` lives in Core and is optional on persisted messages; legacy archives still load. Views consume these neutral types and call generic AppStore actions. Codex wire types and mappings are entirely in OctoAgents.

Each harness owns its connection. Pending requests have fresh local UUIDs bound to the connection, turn generation, and typed wire request ID. Requests for another thread/turn are not presented. Duplicate IDs on a connection are ignored, including after resolution; a provider must use fresh IDs. Responses revalidate current ownership and values. Resolution, interruption, disconnect, completion, and shutdown invalidate pending UI. A prior card cannot answer a later request, even if remote thread/turn/request IDs repeat on a new connection. Startup checks after async version/initialize/thread calls prevent shutdown from launching a new server. AppStore also guards late send failures with the local run generation.

MCP activity uses connection/turn/item identity and updates one transcript entry. Duplicate starts, repeated progress/completion, and progress after terminal status are ignored. Unfinished calls become interrupted when the connection/turn ends. Restored running activity becomes historical interrupted activity on archive load, and shutdown writes activity after harness cleanup. Command/file approval closures now also check current identity before responding. Existing sandbox and reviewer mapping is retained; no permissive launch flags were introduced.

Result details are literal text, bounded to roughly 8 KiB of characters per update (plus truncation marker), with up to 16 content blocks, 16 array elements, 32 object keys per level and five structured levels. Arguments, `_meta`, binary content, and embedded app resources are omitted. Common credential keys and bearer/token patterns are redacted before display/persistence. Arbitrary prose can still contain unrecognized sensitive material; this is not a general secret detector. Raw request bodies and responses are not logged by the bridge.

## Configuration and setup

`CodexExecutable` chooses a custom executable first, otherwise the supported desktop bundle path and then PATH. The selected executable is used for model discovery and generation. `JSONLineProcess` starts `["app-server"]` in the thread checkout, inheriting Octo's process environment, including HOME/CODEX_HOME, with only the existing PATH augmentation and NO_COLOR override. It does not source a login shell or alter config/auth files. Fixture assertions verify cwd (including macOS `/tmp` canonicalization), inherited HOME, argv and unchanged permission/reviewer parameters.

Codex loads its own host configuration (normally `~/.codex/config.toml`, or the configured CODEX_HOME) and trusted project configuration. The CLI decides project trust and managed policy; Octo does not grant trust. A GUI process may have different environment variables from a terminal shell. Settings → Agents identifies the selected executable/version; run that executable in the same project/environment when diagnosing differences. Existing active work is not restarted for inspection.

Use the owning CLI's existing workflows in Octo's ordinary terminal: `codex mcp --help`, `codex mcp list`, `/mcp` in its TUI, and `codex mcp login <server-name>` when that server requires OAuth. The terminal's PATH may select a different installation; use the full executable path shown in Settings when needed. These are user-operated setup actions, not actions Octo performs automatically. No credentials are copied or exposed in an inventory screen.

| Observed failure | What it means / next check |
| --- | --- |
| Tool not advertised or unavailable | Check the selected CLI's enabled integrations, account, environment and project trust. Approval UI cannot install a missing tool. |
| Connection, pipe, socket or service failure | The owning service/transport failed; inspect its CLI diagnostics. App authorization does not repair transport. |
| macOS Accessibility or Screen Recording denied | OS permission for the CLI/service is distinct from target-app consent. Only the user grants OS permissions. |
| Target app requires authorization | A supported request appears in Octo; choose the advertised scope explicitly. |
| Unsupported request/schema | Octo reports a visible notice and refuses it. Use the owning CLI workflow or add a tested adapter mapping. |
| Authentication or setup error | Use the selected CLI's login/MCP workflow. Octo does not collect tokens or automatically run auth. |

The app shows provider diagnostics without claiming every error is a connection failure. It does not infer an OS permission grant from a successful app decision.

## Claude Code protocol evidence (2026-10-05)

Implemented and initialized against installed **Claude Code 2.1.289**. The CLI SDK control stream has no negotiated protocol version; this is the verified CLI baseline, not a claim of compatibility with all historical releases. `claude --help` lists streaming input/output, partial messages, model and effort flags. The official [Python SDK transport](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/transport/subprocess_cli.py), [control request routing](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/query.py), and [typed control requests](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/types.py), inspected on this date, establish `--permission-prompt-tool stdio`, initialize, success/error envelopes, `can_use_tool`, `updatedInput`, deny and provider cancellation. See [official SDK permission guidance](https://code.claude.com/docs/en/agent-sdk/permissions). Octo does not install or bundle the SDK.

A no-prompt initialize probe using the adapter's launch arguments returned model values/display names, `supportsEffort` and `supportedEffortLevels`. Manual mode normalizes to the CLI's `default` permission mode. Octo exposes Manual and Auto, mapping the neutral `ask` and `autoReview` intents respectively to `manual` and `auto`. Auto is the default when no choice is saved; explicit saved choices remain intact. The CLI’s initialize response supplies `current_permission_mode`: Auto must be confirmed before user input is submitted, and mismatches or missing Auto confirmation fail visibly. Catalog discovery uses Manual independently. If a subsequent `system/init` reports a different `permissionMode`, Octo shows a visible notice. CLI-configured rules and managed policies remain in effect; Claude owns classifier decisions and its OS sandbox. No bypass, client-side automatic approval, allowed-tool expansion, configuration/auth rewrite, hook replacement or MCP override is added. Configured CLI hooks may run during initialization; catalog discovery starts a separate CLI but submits no user/model prompt. A normal-access authentication check confirms the CLI is signed in; the initial sandboxed check could not see its Keychain credentials. Real generation, approval enforcement and resume remain unverified because no live prompt was sent.

Questions accept one to four unique bounded question strings, each with two to eight unique choices and optional user-written text. Multi-select and malformed formats are explicitly denied. Replies return the exact original tool input plus `answers`, keyed by the original question strings; approval decisions never add `updatedPermissions`. Cancellation removes cards without responding to abandoned requests. Unknown control requests receive a protocol error and visible notice. Native tool details use the same bounded redaction helper as Codex; binary results and full arguments are omitted. Claude owns the execution and permissions of configured MCP tools; generic forms, app-access scopes, inventory and computer-use cleanup are not implemented for Claude.

## Claude authentication and product policy review (2026-10-05)

The adapter starts the user's installed, unmodified Claude Code executable with its normal CLI configuration and authentication. Octo does not implement a Claude.ai login, read/extract/store subscription tokens, send direct authenticated requests to Anthropic, spoof client headers, resell/relay another user's subscription, or override CLI usage limits. Published SDK source supplies the stream/control framing; the binary is not decompiled or patched.

Anthropic's current [legal/compliance guidance](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use) expressly distinguishes prohibited third-party collection/intermediation of Claude.ai credentials from an end user signing into the unmodified binary with their own subscription, including on a host platform. Its [plan/SDK help article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) has a June 15 update pausing the previously announced billing change: SDK, `claude -p`, and third-party app usage continue to draw from subscription limits. The superseded monthly-credit proposal below that update is not current policy.

This supports an interpretation that ordinary individual local use through Octo fits the documented end-user CLI path. It is not a legal opinion, approval from Anthropic, assurance of zero account-enforcement risk, or authorization for prohibited tasks. Anthropic's [Usage Policy](https://www.anthropic.com/legal/aup) and applicable account terms still govern what the user does. The [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview#get-started) also restricts third-party developers offering Claude.ai login/rate limits for products; Octo provides no application-owned Claude.ai login flow; the Settings terminal launcher described below opens the unmodified CLI’s own sign-in flow.

Distribution is a separate requirement: the legal/compliance page's product-hosting section requires Commercial Terms, unmodified binaries, all built-in authentication methods retained, per-user credentials/direct billing and no resale/intermediation. No launch, publish or distribution approval is claimed by this implementation. The provider label uses **Claude Agent**, one of the [SDK's permitted dropdown labels](https://code.claude.com/docs/en/agent-sdk/overview#branding-guidelines), while documentation accurately identifies the installed executable as Claude Code. No Anthropic logos or endorsement claims are added. Recheck these sources before distributing or changing authentication/billing behavior.
